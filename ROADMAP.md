# Roadmap — InvoiceFlow

> Статус на 25 июля 2026 года. Это живой план, а не описание уже поставленных возможностей. При завершении каждого пункта нужно обновить этот файл, `docs/CURRENT_TASK.md`, `docs/API_CONTRACT.md` и, если решение меняет границы системы, `docs/DECISIONS.md`.

## Цель продукта

InvoiceFlow превращает PDF/JPG/PNG-счёт в **структурированное предложение для проверки человеком**. Оригинал остаётся доступным для сверки, правки создают неизменяемые версии, а экспорт возможен только из явно утверждённой версии.

Продукт демонстрирует надёжную обработку документов, а не бухгалтерскую систему: он не оплачивает счета, не подключается к банкам и не делает финансовые решения автоматически.

## Где проект находится сейчас

Завершены этапы 0–7. Репозиторий не прототип: Go API и worker, PostgreSQL, React/Vite-интерфейс, Docker Compose, зелёный CI (Go + integration + frontend). Проверенная сквозная цепочка: **загрузка → durable processing → извлечение → `needs_review` → неизменяемая human-review версия → утверждение точной версии → CSV / signed webhook экспорт**, интерфейс раздаётся из API (`WEB_DIR`, ADR-013) с честным лендингом и media asset из реального приложения.

Внешнее ревью 24 июля 2026 подтвердило это на живом стенде: `go test ./...`, 29 фронтовых тестов и `tsc -b` зелёные; `docker compose up --build --wait` поднимается; загрузка `fixture-cedarline-services.pdf` доходит до `needs_review` ровно с одним обещанным `subtotal_tax_total_mismatch`. Инженерные границы (durable jobs, точные деньги, неизменяемость, безопасность раздачи и вебхуков) претензий не вызвали.

Этап 8 (демо-опыт и презентация репозитория) и этап 9 (трассируемость, метрики, точность документации) закрыты полностью, кроме самого развёртывания публичного стенда. По ADR-017 каждый ответ API несёт `X-Request-Id`, который совпадает с id в конверте ошибки и в единственной строке access-лога, а worker умеет отдавать базовые метрики на отдельном приватном адресе (`METRICS_ADDR`, по умолчанию выключено). Осталось единственное: поднять публичный стенд — это требует аккаунта на площадке и учётных данных.

### Этап 8 — демо-опыт и презентация (завершён, кроме развёртывания)

Этапы 0–7 закрыли инженерную часть. Этап 8 закрывает разрыв между качеством кода и первым впечатлением: сейчас посетитель портфолио видит в корне промпты для агентов, а загрузив собственный счёт — пустую форму. Ни один пункт ниже не меняет доменные инварианты.

#### P0 — блокируют ценность демо

- [x] **Офлайн-fallback экстрактор для незнакомого документа.** Реализовано в ADR-015. `FallbackStructuredExtractor` спрашивает реестр фикстур первым и обращается к `HeuristicStructuredExtractor` только когда тот не вернул ни одного кандидата (триггер — `Proposal.HasCandidates()`, форма результата, а не код диагностики, поэтому цепочка провайдер-нейтральна). Ридер детерминирован, офлайн, без состояния и устроен так, что его отказ — это молчание, а не выдумка: неоднозначные даты через слэш пропускаются, процент никогда не читается как сумма, построчный налог остаётся неизвестным, а имя поставщика предлагается только при подтверждении другим полем. Доказательства правдивы по построению — цитируется та самая строка источника, поэтому серверный `ValidateEvidence` проходит на реальных данных. Живая проверка: незнакомый счёт Northwind даёт supplier/email/номер/обе даты/валюту/subtotal/tax/total и обе позиции таблицы, `71.00 + 13.49 = 84.49` — без ложных предупреждений. Побочно исправлено: `pdftotext` получил `-layout` (без него Poppler отрывал каждую метку от её суммы) и процент больше не читается как сумма. Все фикстуры сохранили побайтово идентичные снимки, Compose smoke зелёный.
- [x] **Убрать агентную обвязку из корня публичного репозитория.** `MASTER_PROMPT.md`, `MASTER_PROMPT_PREMIUM_DESIGN.md`, `MODEL_ROUTING.md`, `MANIFEST.json`, `START_HERE_RU.md`, `gitignore.fragment`, `.kiro/` и `.codex/` перенесены в `.internal/` (в `.gitignore`, файлы остались на диске); `scripts/check-agent-pack.py` переехал туда же с обновлёнными путями, а `agent-pack` убран из `make check` как локальная проверка обвязки, а не product gate. В корне остались `README.md`, `ROADMAP.md`, `LICENSE`, `Makefile`, `Dockerfile`, `docker-compose.yml`, `go.mod`/`go.sum` и каталоги продукта. `AGENTS.md`, `CLAUDE.md` и `.claude/agents/` оставлены сознательно: это стандартные для современного репозитория файлы конфигурации агентов, а не промпты-инструкции, и перенос `CLAUDE.md` сломал бы загрузку инструкций проекта. #### P1 — соответствие собственной спецификации

- [x] **Warnings о недостающих обязательных полях.** `missingFieldWarnings` в `internal/invoices/normalize.go` выдаёт `missing_required_field` для `supplier_name`, `invoice_number`, `issue_date`, `currency` и `total`. Проверяется **сырой** кандидат, а не нормализованный результат, поэтому присутствующее-но-отклонённое значение сохраняет свой конкретный warning (`invalid_date`, `invalid_money`, `unsupported_currency`) и не считается дважды. `subtotal` и `tax` сознательно не обязательны: множество законных счетов указывают только итог, а лишние предупреждения приучают ревьюера их игнорировать. Пустое предложение больше не проходит молча. Код добавлен в перечень на лендинге и в `docs/API_CONTRACT.md`.
- [x] **Привязать warnings к полям формы.** `ReviewWorkspace` строит индекс `field → warnings[]` и рендерит предупреждения на самом поле — `aria-invalid`, `aria-describedby` и амбер-рамка из существующих токенов, включая построчные адреса вида `line_items.0.total`. Список предупреждений внизу остался как сводка. Важная деталь, которую поймал тест: список предупреждений вынесен **за** `<label>`, иначе его текст попадал в доступное имя поля вместо описания.
- [x] **Список документов.** `GET /api/v1/documents` отдаёт bounded-страницу с keyset-пагинацией по `(created_at, id)`, а не offset: вставка нового документа во время листания не может продублировать или потерять строку. Размер страницы зажимается сервером (20 по умолчанию, максимум 100), курсор непрозрачный и валидируется — чужой курсор даёт `400 invalid_pagination`, а не тихий возврат на первую страницу. Проекция presentation-safe: без SHA-256, object id, storage key и внутреннего UUID версии; интеграционный тест это проверяет. На `/app` — таблица с поставщиком, номером, точной суммой из минорных единиц (целочисленная арифметика, без float), статусом и временем, плюс «Load more».

### Этап 9 — дистрибуция, трассируемость и точность документации (завершён, кроме развёртывания)

Аудит репозитория 25 июля 2026 не нашёл ни одного дефекта доменных инвариантов. Найденное делилось на три группы: проект **не доходит до читателя** (нет публичного стенда), **не трассируется в эксплуатации** (`request_id` выдавался, но нигде не логировался; метрик не было, хотя они заявлены в собственном MVP-скоупе) и **занижает себя в документации** (README отрицал уже реализованные возможности).

**Состояние:** закрыто всё, кроме самого развёртывания (P0), которое требует аккаунта на площадке и учётных данных и остаётся действием владельца. Эксплуатационная поверхность, добавленная в P1, зафиксирована в **ADR-017**. Ни один пункт не изменил доменные инварианты, схему БД и публичный контракт данных.

Проверено в этом проходе: `gofmt`, `go vet ./...` (в том числе `-tags=integration`), `go test ./...` и фронтенд-гейт (`format:check`, `lint`, `typecheck`, 42 теста, `vite build`). **Не перепроверялись:** PostgreSQL-integration, Compose smoke и новый браузерный E2E — демон Docker на машине был выключен.

#### P0 — проект не доходит до читателя

- [ ] **Развернуть публичный стенд.** Это единственный пункт с непропорционально высокой отдачей: заказчик на фрилансе почти никогда не клонирует репозиторий, поэтому ссылка конвертирует «выглядит серьёзно» в «я это потрогал» лучше, чем любая следующая фича.
  - **Вся подготовка завершена.** Форма развёртывания выбрана и закоммичена (амендмент к ADR-016): один хост с уже существующими Compose-файлами плюс `docker-compose.public.yml` и каталог `deploy/` (nginx с реальным пер-визиторным лимитом, `reset.sh`, systemd-таймер ночного стирания). Выбор определён одним ограничением: S3-адаптера нет, `STORAGE_DIR` — общая файловая система для `api` и `worker`, а PaaS обычно даёт диск ровно одному сервису. `docs/DEPLOYMENT.md` содержит пошаговую инструкцию и чек-лист. Ничего из этого не требует изменений в приложении и не стоит денег: бесплатны и хост (always-free VM), и имя (бесплатный поддомен + Let's Encrypt).
  - **Осталось только исполнение.** Нужны аккаунт на площадке, имя хоста и учётные данные, и оно публикует стенд в интернет — поэтому выполняется владельцем, а не агентом.
  - Критерии приёмки: пройден чек-лист `docs/DEPLOYMENT.md`; БД эфемерная, без постоянного тома; `EXTRACTOR` не задан (офлайн); включён `PUBLIC_DEMO=true` и баннер виден; `WEBHOOK_SECRET` сгенерирован, а не взят из репозитория; лимит настроен на прокси, а не только в процессе; ночной сброс проверен фактическим стиранием; метрики недостижимы снаружи; ссылка добавлена в шапку `README.md` и в `docs/DEPLOYMENT.md`.
  - Критерии приёмки: пройден чек-лист `docs/DEPLOYMENT.md`; БД эфемерная, без постоянного тома; `EXTRACTOR` не задан (офлайн), `WEBHOOK_URL` не задан; включён `PUBLIC_DEMO=true` и баннер виден; настроен лимит на самой площадке, а не только в процессе; настроен регулярный сброс; ссылка добавлена в шапку `README.md` и в `docs/DEPLOYMENT.md`.

#### P1 — соответствие собственной спецификации

- [x] **Логировать `request_id` и запросы API.** Реализовано в **ADR-017**. Раньше `writeAPIError` генерировал `request_id` в момент записи ответа, и это значение не попадало ни в один лог: аффорданс был, трассировки не было — клиент мог назвать id, который нигде не найти. Теперь `withRequestContext` (`cmd/api/middleware.go`) присваивает id **на входе**, отдаёт его в `X-Request-Id`, кладёт в `context` и пишет ровно одну структурированную строку на запрос — `method / path / status / duration_ms / request_id`. `writeAPIError` берёт id из контекста вместо генерации собственного, поэтому значение в теле, в заголовке и в логе — одно и то же; тест это и проверяет, второй тест проверяет ровно одну запись лога на запрос. Путь контролируется клиентом, поэтому он обрезается до 200 байт, сводится к печатаемому ASCII, а query-строка отбрасывается целиком; тело запроса, имена файлов, storage keys, текст документа и секреты в лог не попадают. Если middleware не установлен (хендлер, собранный прямо в тесте), `requestID` возвращает свежий id — конверт ошибки никогда не уходит без него.
- [x] **Базовые метрики.** Реализовано в **ADR-017**; это было единственное место, где проект не выполнял собственную декларацию из `AGENTS.md`. `internal/metrics` — маленький реестр без зависимостей, рендерящий текстовый формат Prometheus: `invoiceflow_process_jobs_total` и `invoiceflow_export_jobs_total` по терминальному исходу (`success`, `retry`, `dead_letter`), гистограмма `invoiceflow_extraction_duration_seconds` с границами вокруг таймаутов PDF (15 с) и OCR (30 с), плюс gauge-и `invoiceflow_documents` и `invoiceflow_jobs` по статусу — глубина очереди это серия `ready` второго. Важнее списка две вещи. Счётчики срабатывают из необязательных хуков `Worker` **только после того, как долговременный переход зафиксирован**, поэтому счётчик никогда не заявляет исход, которого нет в базе; чтобы `dead_letter` был точным, а не выведенным, `FinishRetry` и `FinishExportRetry` теперь возвращают зафиксированный исход. Gauge-и читаются в момент scrape через `SELECT status, count(*)`, а не считаются в памяти, поэтому перезапущенный worker сразу показывает правду, а не считает с нуля; сбой одного запроса рендерится комментарием и глушит только себя, и сообщение драйвера в экспозицию не попадает. Эндпоинт принадлежит **worker**-процессу и слушает отдельный адрес `METRICS_ADDR`, по умолчанию пустой — без явной настройки не открывается вообще. Аутентификации у него нет, а объём трафика он раскрывает, поэтому конфигурация отказывается принять адрес, равный `API_ADDR`: это ровно та ошибка, которая тихо опубликовала бы эксплуатационные метрики на публичном стенде из ADR-016.
- [x] **Убрать устаревшие утверждения из README и `docs/CURRENT_TASK.md`.** Все расхождения занижали проект. Строка **Scope** в таблице ограничений README утверждала «No document list/search», хотя список с keyset-пагинацией поставлен на этапе 8; строка статуса всё ещё говорила «Stages 0–7». `docs/CURRENT_TASK.md` по той же причине числил `document list/search` нереализованным. Теперь каждая строка называет только то, чего действительно нет — поиск и ручной retry, — а упоминание отсутствующих метрик убрано, потому что метрики появились.

#### P2 — качество и защита от регрессий

- [x] **Поднять unit-покрытие `internal/processing`.** 4.1% → 10.6%. Вынесены решения, которым база данных никогда не была нужна: `clampDocumentPageSize`, `requireNeedsReview`, `requireExportableVersion` и два построителя ключей идемпотентности экспорта. Они покрыты напрямую вместе с round-trip курсора, `validUUID`, санацией диагностик и классификацией ошибок обработки. Транзакционные пути осознанно остаются за integration-тестами — это их место.
- [x] **Исключить `web/node_modules` из области Go-модуля.** `go.mod` получил директиву `ignore ./web/node_modules`, и `go list ./...` больше не показывает `flatted` — чужой Go-пакет внутри npm-зависимости.
- [x] **Убрать `act()`-warning из фронтовых тестов.** Тест файлового инпута в `routes.test.tsx` рендерил оболочку без мока `fetch` и без ожидания, поэтому запросы на монтировании завершались уже после тела теста. Прогон снова чистый.
- [x] **E2E-тест в браузере.** `web/e2e/review-flow.spec.ts` проводит в Chromium полный путь «загрузка → review → правка → утверждение → скачивание CSV» и вторым тестом проверяет, что документ достижим из списка, а не только по URL, который вернула загрузка. Загружается *сгенерированный* вымышленный счёт, а не коммитнутая фикстура: загрузки дедуплицируются по SHA-256, поэтому фикстура на втором прогоне дала бы `409`, а незнакомый документ вдобавок проходит через эвристический ридер ADR-015 — тот самый путь, которым идёт реальный посетитель. Набор намеренно вне `make check`, потому что требует запущенного стенда; `make test-e2e` и `web/playwright.config.ts` описывают, как направить его на изолированный инстанс.
- [x] **`ReviewWorkspace.tsx` → `useReducer`.** Шестнадцать `useState` стали одной машиной состояний в `web/src/components/review/reviewState.ts`. Восемь из тех булевых флагов описывали два факта — какое необратимое действие подтверждается и какое выполняется, — и оба однозначны по построению, поэтому представление их одним значением каждое убрало состояния, недостижимые на практике, но требовавшие рассуждения. Восемь тестов редьюсера покрывают переходы, которые легче всего сломать: неудачное действие оставляет свой диалог подтверждения открытым, сбой фонового обновления не стирает ревью, над которым человек уже работает, а ручное обновление перезапускает ограниченный счётчик опроса, не теряя отслеживаемый экспорт.

Не входит в этап 9: аутентификация, raster OCR, S3-адаптер, multi-tenant. Они остаются в backlog ниже.

## Неподвижные правила

- AI/OCR и пользовательский ввод — недоверенные данные; они не задают статус документа, storage key, актёра, секрет или destination webhook.
- Деньги представлены точно (integer minor units / `money-v1`), а не `float`.
- Оригинал, extraction/review versions и audit events не изменяются задним числом.
- Approval адресует ровно одну неизменяемую версию; экспорт адресует ровно утверждённую версию.
- Внешняя доставка at-least-once: идемпотентность обязательна, «exactly once webhook» не заявляется.
- Демо работает без платных ключей и использует только фиктивные документы/данные.
- Новый этап не расширяется неявно: сначала acceptance criteria, затем код, тесты, документация и review diff.

## После portfolio release — отдельный backlog

Эти работы не являются обещанием ближайшего MVP. Каждая требует отдельной оценки, ADR и threat model.

| Приоритет | Направление | Почему отдельно |
| --- | --- | --- |
| P0 для production, не для demo | Authentication/authorization, actor identity, document-level access control, roles | Текущий local demo сознательно использует fixed actor и не делает production security claim. |
| P0 для production | Least-privilege DB roles, secrets management, observability/metrics, backup/retention/runbooks, stronger process sandbox/malware controls | Эти меры меняют эксплуатационную модель, а не только UI. |
| P1 | PDF raster OCR с page/pixel accounting, безопасный live provider adapter | Нельзя «включить» без нового resource/security design. |
| P1 | Поиск по документам, manual processing retry и операторский UX | Список с keyset-пагинацией уже реализован на этапе 8; остальное нужно для потока документов, но не должно смешиваться с этапом approval/export. |
| P1 | S3/MinIO storage adapter, managed webhook destinations | Потребуют управления конфигурацией, секретами и deployment model. |
| P2 | Multi-tenant boundaries, extra accounting integrations, analytics | Не входят в текущую продуктовую цель и могут разрушить ясность portfolio demo. |

## Как вести roadmap

1. Перед началом пункта перенести его точную цель, scope, invariants и test plan в `docs/CURRENT_TASK.md`.
2. Сначала принять решения, меняющие данные, доверенные границы или публичный API; после — миграции и код.
3. Реализовывать вертикальным срезом: migration → repository/domain → worker/API → UI → tests → smoke → docs.
4. Не помечать пункт «готово» по наличию кода: обязательны проверка failure paths, зелёные релевантные тесты и review diff.
5. После релиза пересматривать план по фактическим ограничениям, не по желаемым marketing claims.
